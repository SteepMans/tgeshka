# Транспорт через шлюз

TGeshka ходит в Telegram только через шлюз. Каждое MTProto-соединение tdesktop к DC (основная сессия,
медиа, загрузки и выгрузки, временные ключи, CDN) открывается отдельным WebSocket по TLS на адрес шлюза.
Внутри идут те же байты, что tdesktop слал бы в TCP-сокет к DC: 64 байта инициализации obfuscated2 и дальше
зашифрованный поток MTProto-транспорта (abridged, `Version0`, без секрета). Шлюз берёт номер DC из
инициализации и передаёт поток на DC. Сам шлюз в этот репозиторий не входит, адрес по умолчанию в исходниках
пустой (см. «Адрес шлюза» ниже).

```
tdesktop ──WSS (TLS, SNI = домен шлюза)──▶ шлюз ──TCP──▶ DC Telegram
```

## Как устроено

| Файл | Что делает |
|---|---|
| `mtproto/mtproto_gateway.h/.cpp` | настройки шлюза (URL, токен), переменные окружения, события об ошибках шлюза |
| `mtproto/details/mtproto_gateway_socket.h/.cpp` | `GatewaySocket`: `AbstractSocket` поверх `QSslSocket` со своей минимальной рамкой WebSocket (RFC 6455: маска клиента, binary, ping/pong, close), без модуля QtWebSockets |
| `core/core_gateway.h/.cpp` | `Core::ApplyGateway()` для UI: сохранить настройки и переподключить сессии |

Правки upstream-файлов минимальные:

- `ProxyData::Type::Gateway` (`mtproto_proxy_data.h/.cpp`): внутренний тип, в список прокси пользователя и в
  настройки не сохраняется. Хост и порт шлюза в `host`/`port`, путь в `user`, токен в `password`.
- `Session::refreshOptions()` (`session.cpp`): режим шлюза включён всегда. Сессии получают
  `GatewayProxyData()`, только TCP и IPv4. Прокси из настроек пользователя не используются.
- `TcpConnection::connectToServer()` (`connection_tcp.cpp`): для `Type::Gateway` создаётся `GatewaySocket`,
  секрет протокола пустой, поэтому `Version0`. Адрес DC из конфигурации Telegram уходит в шлюз параметром
  `a=IPv4:порт`, для IPv6 параметр не передаётся.
- `SpecialConfigRequest::performRequest()` и `DomainResolver::performRequest()`: в режиме шлюза запросы
  DNS-over-HTTPS (Google, Mozilla/Cloudflare) и Firebase/Firestore не отправляются.

Upgrade-запрос: `GET <путь>?a=149.154.167.51:443` с заголовком `Authorization: Bearer <токен>`. Токен в URL не
кладётся и в лог не пишется. Сертификат шлюза проверяется системными корнями Qt/OpenSSL, ошибки TLS не
игнорируются. На Ping шлюза (каждые 25 с) сокет отвечает Pong. Close `1000`/`1001` обрабатывается как обрыв
TCP, остальные коды как ошибка соединения. В обоих случаях tdesktop переподключается по своей обычной логике.

## API для экрана настроек

```cpp
#include "core/core_gateway.h"

// Прочитать текущие значения (потокобезопасно).
const auto current = MTP::CurrentGateway();   // .url, .token
current.valid();                               // wss://, есть хост и токен

// Сохранить и переподключиться (главный поток).
Core::ApplyGateway({ .url = url, .token = token });

// Открытое соединение со шлюзом (главный поток).
MTP::GatewayOpened() | rpl::on_next([=] { /* статус «Подключено» */ }, lifetime);

// Ошибки шлюза для показа пользователю (главный поток).
MTP::GatewayErrors() | rpl::on_next([=](MTP::GatewayError error) {
	// error.code: коды Close из протокола (4401 токен отозван, 4429 лимит
	// соединений, 4502/4504 недоступность ноги или DC, ...)
	// или MTP::kGatewayNoToken, kGatewayRejected (HTTP вместо 101,
	// например нейтральная 404 при неверном токене), kGatewayTlsError.
}, lifetime);
```

- У транспорта нет адреса по умолчанию: пустой `url` значит, что соединения не открываются.
- Хранить URL и токен в своих настройках (Core settings или отдельный файл) и при старте приложения, до
  первого подключения, вызывать `Core::ApplyGateway()`. Пока он не вызван, действуют переменные окружения.
- Без адреса или токена соединения сразу завершаются ошибкой, прямых подключений нет. `GatewayErrors()`
  присылает `kGatewayNoToken`. По нему можно открыть экран ввода ключа.
- Экран прокси upstream в этом режиме ни на что не влияет, его стоит скрыть.

## Адрес шлюза

В исходниках адреса шлюза нет. Его можно задать:

- при сборке: `-DTGESHKA_GATEWAY_URL=wss://...` для CMake (`build.ps1` берёт его из `-GatewayUrl`, переменной
  окружения `TGESHKA_GATEWAY_URL` или файла `%USERPROFILE%\.config\tg-fork\gateway.txt`, CI берёт его из секрета
  `TGESHKA_GATEWAY_URL`). Такой адрес подставляется по умолчанию;
- ссылкой `tgeshka://gateway?url=<wss://...>&token=<ключ>`: она сохраняет и адрес, и ключ;
- вручную на экране первого запуска или в настройках, раздел TGeshka.

Если адрес не задан ни при сборке, ни ссылкой, экран первого запуска просит адрес и ключ.

Проверка ключа до входа: `GET https://<хост шлюза>/v1/info` с заголовком `Authorization: Bearer <ключ>`
(200: ключ действителен, 404: нет).

## Разработка

| Переменная | Значение |
|---|---|
| `TGGW_URL` | адрес шлюза, например `wss://gateway.example.com/v1/stream` |
| `TGGW_TOKEN_FILE` | путь к файлу с токеном `tc_...` |

Переменные читаются при первом подключении и действуют, пока UI не вызовет `Core::ApplyGateway()`.
Логи соединений видны с ключом `-debug` (`DebugLogs/mtp_*.txt`, у сокета суффикс `_gw`).

## Что идёт мимо шлюза

- Звонки (tgcalls): в v1 подключаются к серверам Telegram напрямую (TODO в `mtproto_gateway.h`).
- Веб-содержимое, не относящееся к DC: веб-страницы и мини-приложения во встроенном браузере, предпросмотр
  внешних ссылок, `file_download_web` (файлы с внешних сайтов), карты и геолокация.
- Автообновление и отчёты о падениях upstream ходят на серверы Telegram Desktop. В сборке форка их нужно
  отключить (`DESKTOP_APP_DISABLE_AUTOUPDATE`, `DESKTOP_APP_DISABLE_CRASH_REPORTS`), иначе обновление поставит
  официальный клиент поверх форка.
