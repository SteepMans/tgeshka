# Обновления TGeshka

TGeshka обновляется сама, через свой шлюз и тем же ключом доступа, что и соединение. К серверам обновлений
Telegram Desktop клиент не обращается: сборка идёт с `DESKTOP_APP_DISABLE_AUTOUPDATE`, из штатного механизма
используется только установщик `Updater.exe`.

## Версии и каналы

- Версия TGeshka задаётся тегом: `v0.1.2` (stable), `v0.1.2-beta`, `v0.1.2-beta.2` (beta). CI передаёт её в сборку
  (`build.ps1 -Version`, макрос `TGESHKA_VERSION`). Версия Telegram Desktop внутри (`AppVersion`) своя и для
  обновлений не используется.
- Порядок: `0.1.2-beta` < `0.1.2-beta.2` < `0.1.2` < `0.1.3-beta`.
- Канал выбирается в «Настройки → TGeshka → Обновления» («Бета-версии»). Stable получает новейший обычный
  релиз GitHub, beta — новейший из всех, включая pre-release (так отдаёт шлюз).

## Релиз

Тег `v*` запускает `.github/workflows/windows.yml`. После сборки шаг Release:

1. Кладёт в zip `TGeshka/tgeshka-version.txt` с версией и называет пакет `TGeshka-<версия>-win64.zip`.
2. `tools/tgeshka/sign_update.js` считает sha256 пакета и подписывает **сырые 32 байта sha256** ключом Ed25519 из
   секрета `TGESHKA_UPDATE_KEY`, пишет `update-manifest.json` (формат — SteepMans/api-gateway
   `docs/update-v1.md`). Необязательный `min_version` берётся из `Telegram/build/tgeshka_min_version`.
3. Публикует оба файла ассетами релиза; бета-теги — как pre-release.

Если у того же коммита уже есть зелёная сборка `main` с артефактом, тег не компилирует заново: job
«Release from main build» на ubuntu скачивает этот пакет, сверяет `tgeshka-version.txt` с тегом, переименовывает в
`TGeshka-<версия>-win64.zip` и выполняет шаги 2–3. Сборка `main` берёт версию из `TGESHKA_VERSION` в
`tgeshka_brand.h`, поэтому пакет берётся, только если версия в нём совпала с тегом. Иначе (например, бета-тег
переведён в стабильный через «Promote beta») тег собирается полностью с версией из тега.

Шлюз перечитывает релизы раз в 10 минут, клиенты видят новую версию при следующей проверке.

Ключ подписи: приватный — секрет `TGESHKA_UPDATE_KEY` и резервная копия у владельца, публичный — в
`Telegram/SourceFiles/tgeshka/tgeshka_update_verify.cpp`. Смена ключа — новая сборка со старым и новым ключом в
клиенте, затем подпись новым.

## Клиент

`Telegram/SourceFiles/tgeshka/tgeshka_update.cpp`:

- Проверка при запуске и раз в 6 часов: `GET /v1/update/manifest?platform=desktop&channel=stable|beta` на адресе
  шлюза, `Authorization: Bearer <ключ>`. `204` — обновлений нет.
- Если версия в манифесте новее своей, пакет качается в фоне с того же шлюза (`url` из манифеста, только путь
  `/v1/update/package/...`), с докачкой через `Range`, в `<рабочая папка>/tgeshka_update/`.
- Пакет принимается, только если совпали размер, sha256 и подпись Ed25519 над sha256 зашитым публичным ключом.
  Иначе файл удаляется, следующая попытка через 15 минут. Версия внутри пакета (`tgeshka-version.txt`) должна
  совпасть с версией манифеста: подпись покрывает только байты пакета, а так старый подписанный пакет нельзя
  выдать за новый.
- Готовое обновление: кнопка «Доступно обновление X — Перезапустить» под списком чатов и в настройках. Если
  перезапуска не было, обновление ставится при следующем запуске.
- Установка: пакет распаковывается в `tupdates/temp`, новый `Updater.exe` заменяет текущий, приложение
  закрывается, `Updater.exe -update` копирует файлы и запускает TGeshka снова. Файл версии для реестра не пишется,
  поэтому `Updater.exe` не трогает ключ удаления Telegram Desktop.
- Перед установкой заменяемые файлы копируются в `tgeshka_update/previous/`. «Вернуть версию X» в настройках
  ставит их тем же `Updater.exe`; версия, с которой откатились, больше не предлагается, пока не выйдет новее.
- `min_version` в манифесте выше своей версии — окно «Нужно обновиться» без закрытия, с кнопкой перезапуска,
  когда пакет готов.

## Обновление с upstream

`.github/workflows/upstream-sync.yml`, каждый день и вручную (можно указать тег):

1. Берёт последний релиз `telegramdesktop/tdesktop` (`releases/latest`, без pre-release). Если тег уже в `main` или
   ветка `upstream/<тег>` уже есть — выход.
2. Ветка `upstream/<тег>` от `main`, `git merge --no-ff` тега. Известные конфликты решаются сами: удалённые у нас
   workflow upstream остаются удалёнными (новые тоже убираются), `README.md` — наш, `core/version.h` и
   `winrc/Telegram.rc` — версия upstream с нашим брендом (`tools/tgeshka/rebrand_upstream.py`).
3. Без конфликтов: PR, сборка `windows.yml` этого коммита. Зелёная — коммит идёт в `main` (fast-forward), ставится
   тег следующей беты (`tools/tgeshka/next_version.sh`), тег запускает релиз. Красная — PR остаётся.
4. Конфликт: конфликтные файлы коммитятся с маркерами в черновой PR, разрешать в этой ветке.
5. Итог — сообщение владельцу в Telegram (секреты `TG_NOTIFY_TOKEN`, `TG_NOTIFY_CHAT`).

Пуши и теги идут через deploy key `UPSTREAM_SYNC_KEY`: история upstream меняет `.github/workflows`, а это
`GITHUB_TOKEN` пушить нельзя, и тег от `GITHUB_TOKEN` не запустил бы сборку релиза. Теги upstream в репозиторий
не пушатся (они тоже `v*`).

В stable бета переходит вручную: workflow «Promote beta» (`.github/workflows/promote-beta.yml`) ставит тег
`vX.Y.Z` на коммит последней (или указанной) беты.
